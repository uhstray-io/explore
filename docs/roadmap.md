# Roadmap and handoff

Status as of 2026-11-27. Start here in a new session. The GitHub issues are the source of truth for each feature; this page records what they cannot: branch state, the owner's decisions, known defects and why the plan looks the way it does.

## Where the plan lives

- Planned features are issues #1–#69 on [uhstray-io/explore](https://github.com/uhstray-io/explore/issues). Tracking issue [#70](https://github.com/uhstray-io/explore/issues/70) groups them, lists the foundations to land first, and lists what was considered and not planned.
- Titles carry a short ID from the planning list, such as `B9: Help me answer`. Issues refer to each other by these IDs and by number.
- Each issue has a summary, current behaviour with `path:line` references, proposed behaviour, acceptance criteria, out of scope, implementer notes, **Depends on** and **Related** links, and the base branch and checks. References were checked against `rename-to-explore` on 2026-11-27 and drift as work lands.
- Labels: `area: …`; `size: S`, `S-M`, `M`, `L` (rough estimates); `runs: app` (works with no agent connected), `runs: agent` (a new job type or result format, so it needs a listening agent) or `runs: app+agent`; `origin: copilot-explore` or `origin: new idea`; `foundation`; `changes-invariant`.
- Pick an issue whose **Depends on** issues are closed. X1 ([#1](https://github.com/uhstray-io/explore/issues/1)) comes first: it defines job types, map-level jobs, actions without a node and the shared `ideas/settings.json` once, so features built in parallel share one design. H3 ([#32](https://github.com/uhstray-io/explore/issues/32)) comes next: shared maps make outside changes from `git pull` routine.

## How the plan was made

- Features were adapted from the owner's GitHub Copilot plugin, [Copilot Explore](https://github.com/AndrewGodlewsky/Copilot-Explore), reviewed at commit `af0117b` (docs, code and all closed issues), plus new ideas. The owner chose 68 of 83 candidates; X1 was added as shared groundwork.
- Only behaviour is adapted. The owner dislikes Copilot Explore's UI and visual design, so UI work follows the Constellation design in `skills/explore/assets/`.
- Copilot Explore starts its own model sessions; Explore cannot. Every AI feature is therefore a job type in the existing queue (`cli.mjs next`) and runs only while an agent is listening.

## Decisions made with the owner (2026-11-27)

The owner settled every open decision on 2026-11-27. Where an issue body still describes the earlier design, these decisions win until the issue is edited.

### Product rules

- **Everything about an exploration lives in the repo.** Maps, version history, positions, settings, and pin and archive state are committed, so anyone who clones or pulls gets the same experience and can continue any finished or half-finished map. "Multiplayer" means taking turns through Git; #33 handles parallel edits. Only the server token and connection, the server lock, and live job claim keys stay in `.explore/`, because they are credentials or live process state that nobody else can use.
- **The tree is simple and frictionless.** There are no approval steps. Actions start once the user chooses them. Each question, finding or idea has one ⋯ menu for secondary actions. Advanced options stay out of the way.

### Limits decided while building

- **Challenge decisions opens from Map tools in its own dialog (F2 #25).** The issue adds **Challenge decisions** to Map tools with the answer selector, preview and results. It opens a dialog from there, as the other map-wide tools do, since the hypotheses with their sources and Keep or Dismiss need the room. **Explore this as a direction** closes it and opens Add a direction on the first idea the hypothesis cites that still exists (unfolding it as Find an idea does), prefilled unless the user already has a draft there; only submitting that form adds the direction, which stays inactive. The newest challenge is shown in full, and earlier ones with a point still waiting or kept stay under Earlier challenges. The preview lists the exact answers the agent will read, and says it also gets the map's title, goal and agreed terms, as every map job does. Check answers and Challenge decisions are one answer review in `map-jobs.mjs` (`answerReviewJob`): the same packet, checks and proposal, so both reject a result with fields they do not take, and both fail at claim time, with the reason, when a chosen answer was set aside meanwhile. A review is stale when a question it read changes (an answer, how sure the user is of it, or an open question being answered), not when another question on the same idea is answered. Explore this as a direction replaces an earlier hypothesis's prefill the user left as it was, and keeps a draft they typed, saying so.
- **Decision records open from Map tools, and saving is its own action (F5 #27).** The issue puts **Draft ADR** in Map tools with the selector and preview. It opens a Decision records dialog from there, as the other map-wide tools do, since the editable draft and the save preview need the room. Accepting uses F1's `review-proposal`, which now lets a job type review its own editable item: the ADR type saves the user's text, once. Saving is an action only the ADR route can run: the Store passes it the workspace, and the action route never does, so an agent's `act` can never write a file. The route itself is the browser's; like every user-only action, an agent is told never to call it. If the map cannot be saved after the file was written, the file is taken back, so a retry never leaves a second copy; once the map is saved, the file stays even if a version or the readable views then fail to write.
- **Implementation handoff opens from Map tools in its own dialog, and shares the decision record's groundwork (F4 #26).** The issue adds **Implementation handoff** to Map tools; it opens a dialog from there, as the other map-wide tools do, since the format, the records, the editable draft and Copy and Download need the room. The format travels as `options.format`, so the job preview takes an `options` parameter too and stays the packet the agent reads. The choice of records, the packet that shortens them together, the cited refs and the editable item's Accept or Dismiss are one module, `scripts/record-drafts.mjs`, shared with the decision record (F5), whose behaviour is unchanged; in the browser both dialogs run on one controller, `assets/record-draft-dialog.js` (choosing, the preview, queueing, editing, accepting), and add only their own controls; the markup they share, which the Store loads too, is `assets/record-drafts.js`. After a send the decision record still keeps an open Save preview. An accepted handoff may be at most 24,000 characters, like the agent's draft. Copy and Download appear only on the live map, once accepted: from history the footer would describe a map other than the one shown. The footer's date is the day it was accepted, in the user's own time zone, and its revision the map's when it is copied. It labels each record as the user knows it (the question, or the idea's findings), says how settled each is, marks with `*` the ones the agent cited, and flattens every line from the map to one line, so no title or answer can forge a footer line. A stale proposal of any type names its changed sources: the view adds `changed` from each type's `outdatedRecords`, since the browser cannot recompute the answer keys.
- **The inbox opens from Map tools (K8 #54).** The issue placed an **Inbox** control in the workspace tools row. It is a section of Map tools instead, with a count of open thoughts, for the same reason as the other map-wide tools: the tools row already holds Find an idea and four buttons. The dialog has a quick-capture field at the top. Accepting a placement is its own action, `place-thought`, because it applies the placement; the generic Keep of `review-proposal` is refused for a sort-thoughts item, and Dismiss leaves the thought open. A thought edited since it was sorted cannot be placed by that proposal. The proposal shows "changed since your agent sorted it", and the user asks again. The agent reads the thoughts as they are when it takes the work, whole ones only, at most 20, those never sorted before first, so every thought gets its turn, and never one whose suggestion still waits for the user; Undo and restore now include the inbox and every agent proposal with the user's Keep, Dismiss or Accept, so Check answers' points roll back with them; Ask shows F1's preview of that packet before anything is queued.

- **Reconsiderations live on their jobs, and Stop cancels them (C9 #14).** The issue keeps the latest five on the idea as `node.reconsiderations`. They stay on their `reconsider` jobs instead, as Help me answer and Tidy my wording keep their results: the job holds the criteria snapshot and the result, and `job.outcome` records Use revised comparison (`adopted`, at most one per idea) or Keep original (`dismissed`). So the job history is the one record, and queued, running, failed and cancelled come from the job itself. Stopping one is the existing `cancel-job` (the dialog's Stop), not a new `cancel-reconsideration`; like fail and a restart, it never touches the idea's status. A failed or interrupted attempt says so in the dialog. A revised comparison stays in use only while what it read about the idea (its premise, options, recommendation, answers and how sure each is, claims and limitations) and the criteria are as they were when asked; afterwards the original leads again until the user asks again. Accepting a finding changes none of these, so it leaves the revised comparison in use. Keep original also ends an earlier adoption. Asking waits while the idea's own investigation is open, and a result is checked against the options it was asked about. **Compare with my criteria** sits under the options in the inspector, where the comparison is.

- **Asking again opens the earlier help, for Help me answer and Explain this question (Z4 #62).** The issue offers the earlier result with **Show earlier result** and **Ask again** before anything is queued. Here the earlier result is already shown under its question, so asking again from the ⋯ menu simply opens and focuses it, writes nothing, and says so in a toast. **Ask again** sits quietly at the end of every result, earlier research included, and always queues new work. "Nothing it read has changed" means the packet the agent would get now is the one it got: the claim stores a hash of that packet (its idea, answers and how sure they are, nearby ideas and their state, the goal, and the glossary terms that fitted), so any change the packet would show counts, and nothing else does. The Store checks only when the user asks, never when a map is viewed, so large maps cost nothing extra. Only the newest finished result for a question is checked; an older one could only match if the context changed and changed back. Tidy my wording is not reusable: its input is the user's draft, which is rarely sent twice, and a tidy is quick to redo. As the issue says, a request made with the CLI `act` command is never deduplicated.
- **Recording a hypothesis outcome sits in the inspector, under a Record outcome disclosure (K13 #59).** The issue asks for a **Record outcome** control with the three values and a note. It is a disclosure in the hypothesis's own Hypothesis section rather than a button beside the findings, so it stays out of the way until the user has a result. It preselects the agent's proposal when nothing is recorded or the proposal came after the recorded outcome. In **Add a direction**, the choice between a direction and a hypothesis is a pair of options, and "How to test it" appears only once a hypothesis is chosen. Recording an outcome changes no findings. Only a recording that flags (a first refuted or inconclusive outcome, or a change) makes work running on the hypothesis or what rests on it stale. A changed premise (revise) clears the agent's proposal, like the rest of the findings, but keeps the test and the recorded outcomes: they are the user's record, and the new claim gets its own when the user records again. A result's test replaces the stored one, which stays on the earlier job. Recording an outcome flags the findings resting on the hypothesis, as a changed answer does, rather than treating it as a changed premise: their questions stay answerable. "Explore a changed premise" on a finished hypothesis makes a hypothesis with the same test. Changes since a commit, the viewer and the exports show a hypothesis like any idea, without its outcome.
- **Answer in a file sits in Map tools (K11 #57).** The issue placed an **Answer in a file** button in the workspace tools row. It is a section of Map tools instead, with Export open questions and Import answers, for the same reason as the other review tools: the tools row already holds Find an idea and four buttons. The file lists every open question on an unfinished branch, including ones saved for later, rather than only the brief's questions waiting for an answer: an answer saved for later can still be answered, and the file is where a user catches up. A dismissed question is reported and not saved. Importing while viewing growth history or a saved version is refused, since it changes the live map.

- **The assumptions register opens from Map tools (K6 #53).** The issue placed an **Assumptions** button in the workspace tools row. It is a section of Map tools instead, beside Glossary, for the same reason as the other review tools: the tools row already holds Find an idea and four buttons. A note on what would disprove an assumption opens from an Edit or Add button beside "Would change if", as glossary edits do, so a poll never closes it. The register lives in `assets/assumptions.js` rather than `workspace-view.js`, which keeps only shared view code; the brief and the dialog both read it. Each entry counts what a change to its idea would reach (`changeWalk`, shared with impact), and lists those ideas through `impactOf` only when the user opens the list, so the register does not grow with the square of the map. Like impact, the counts show on the live map only. The note's action lives with the feature in `scripts/assumptions.mjs`. An interpretation on a finding the user cleared is left out, since it is not relied on. In the brief, its section ("Assumptions and interpretations — unverified") replaces "Unsettled answers", which listed the same answers without the agent's interpretations.

- **The source library opens from Map tools (K10 #56).** The issue placed a **Sources** button in the workspace tools row. It is a section of Map tools instead, beside Glossary and Changes since a commit, which open their own dialogs the same way: the tools row already holds Find an idea and four buttons, and the library is a review tool rather than everyday navigation. Node Markdown shows a source's stance only when one is recorded, so existing maps' generated views do not change. The library also lists Help me answer research under the idea and question it serves, labelled and without a stance: `sourceList` ignores one there, since that research has no finding for a source to back. Like earlier results, it never flags and is not counted by stance. In growth history or a saved version the dialog shows the inspector's own read-only note (`readOnlyNote`) and covers the ideas shown.

- **Impact keeps each idea's band, and lists one idea's affected ideas when asked (D4 #19).** The issue's `impactIndex` holds every affected idea for every idea. On a map where most ideas depend on another, those lists grow with the square of the map (90 MB at 2,000 ideas). So the index keeps each idea's band, whether it is open, and why a high one is high, and each idea's walk stops once its band is certain to be high. `impactOf` walks one idea in full for the inspector. The filter's rows give that reason ("At least 5 ideas elsewhere rest on it through dependencies.") rather than the full sentence, which stays in the inspector, because walking every listed idea in full took 7 seconds on a dense 2,000-idea map. An idea's branch is what `contains` links alone reach, so an idea reached both ways counts as in this branch and shows its branch path, even where a dependency reaches it in fewer steps. An idea reached only through dependencies shows a shortest path. Impact is shown on the live map only. Growth history shows today's content, and a saved version is read-only, so nothing there can be settled.

- **Folds are saved with the map (Z6 #64).** The issue's acceptance criteria and out-of-scope list still say folding leaves `map.json` unchanged, but its own view-state section records the owner's 2026-11-27 decision: folds are shared map content like positions. They are kept in `view.collapsed` through the `fold` and `reveal` actions, record no version and are not an outside change. Showing only one branch stays the browser's own. Because folds are shared content, growth history and a version preview never save one: they show the folds of the map shown, as they show its positions, and opening a folded idea there (its ⋯ menu, Right in the outline, or choosing a hidden idea) opens it in this browser only, until the user returns to live. Branch focus works there too. The fold and branch controls are items in the idea's ⋯ menu rather than buttons beside Nearby ideas (one ⋯ menu per item). In the outline, Right and Left open and fold a parent as the tree pattern says, which saves the fold.

- **The Map / Outline switch sits in the canvas heading (Z7 #65).** The issue placed it in the workspace tools row. It sits beside the saved state instead, at the top of the view it changes: the tools row already holds Find an idea and four buttons, and a view switch is not a tool. `outlineRows` lives in `assets/outline.js` with the rest of the outline rather than in `workspace-view.js`, so one module owns it. Without Z6 (#64) rows have no `aria-expanded`, and Left and Right only move.

- **Commands sit in the top bar (Z8 #66).** The issue placed a **Commands** button in the workspace tools row. It sits in the top bar beside Dark mode instead, with Ctrl+K or ⌘K: the palette works across the whole app, and the tools row already holds four map buttons.

- **More filters sit with the progress filters (Z9 #67).** The issue placed the **More filters** button in the workspace tools row. It sits directly under the progress filters instead, inside the same "Find ideas by state" landmark: it is a filter, its results open in the overview list right below, and the tools row holds map-level dialogs that a fifth button would crowd.

- **A map file is at most 64 MiB (J3 #45).** The server neither opens nor saves a larger `map.json`; it is listed as unreadable (`too-large`) and a save is refused with a clear message. One rule in `map-validation.mjs` (`readMapFile`, `maxMapBytes`) serves the server, the validator and the support report. Real maps are far smaller; the limit keeps reads, generated views and CI checks bounded.

- **Result checks reject only certain breaches (K3 #51).** A result is refused for re-asking a question answered anywhere in the map, re-asking one dismissed on the same idea, or repeating a question or suggestion title in one result. A question dismissed on another idea is only a warning (`dismissed-elsewhere`): the agent sees this idea's dismissals but not every branch's, and a dismissal means "not useful here". The issue's rule that heuristics never reject a result stands. Verified by `tests/result-checks.test.mjs`.

- **The benchmark's operator activates nothing, and runs must match exactly (J6 #48).** The issue has the operator accept nothing. The protocol also has them activate and dismiss nothing, so `collect` can fail the self-activation gate on its own: any activated or accepted idea in a run is the agent's doing. The guidance hash covers `SKILL.md` and every Markdown file under `references/`, topic profiles included, since the agent reads those too. `compare` refuses runs of different case-set versions, and also runs whose cases differ under the same version. `collect` reads `map.json` as the server reads it (`readMapFile`) instead of through the Store, so a run is never adopted or rewritten. It reads each round from its job (`job.result`, and the result checks' `resultWarnings`), not from the idea, which keeps only its latest round, and the gates from history. A gate nobody checked is reported as not checked, and `compare` exits 1 unless the "after" run checked and passed every gate, could read every map, and kept every case the "before" run had. The script imports the Store, which imports `git.mjs` and so `node:child_process`; the benchmark never calls it, and a test walks the import graph to keep that the only such module.
