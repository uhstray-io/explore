# Map format v1

Each exploration is saved in `ideas/map-<id>/` inside the working repository:

```text
map.json         canonical snapshot: knowledge, relationships, work, history, layout
README.md        generated overview with source revision and links
nodes/<id>.md    generated readable node detail with source revision
```

Shared settings for every map live beside them in `ideas/settings.json` (`{ version: 1, revision, ...fields }`). Like the maps, the file is meant to be committed.

The JSON snapshot is the only source of truth. Markdown files are readable projections and can be rebuilt by restarting the server. If a generated file's revision differs from `map.json`, treat it as stale. Do not write generated files expecting the UI to ingest the edit.

`schemaVersion` identifies the format; `revision` identifies a saved map state. Stable map/node/job IDs survive title and layout changes. The original user idea is preserved in `originalIdea`; each node's `prompt` records its current premise independently of model-generated `body` findings. Prior premises and research results remain in history/jobs.

Nodes contain `id`, `title`, `kind`, `parentId`, `prompt`, `summary`, `body`, `status`, `reviewState`, `contentRevision`, `questions`, `sources`, and `stale`, and optionally `doneWhen`: the user's stopping point for the branch (K4), set only by the user, shown under the premise and sent to the agent with the branch. Questions retain answers and answer timestamps. An answer optionally records `answerState` (`tentative`, `decided` or `assumption`); a missing state reads as Tentative and is shown as "not recorded", never written on load. Every new question records `askedAt` and `jobId`. A question may carry the agent's `importance` (`low`, `medium` or `high`, never without a reason) and `why` (what its answer would change); without importance it reads as Unranked. Both belong to the question as asked: they are not reassessed, and a superseded question keeps them as history. A changed answer records `changedAt`, from which its follow-ups are dated, and keeps earlier answers in `previousAnswers` (`answer`, `answerState`, `answeredAt` of that answer, `replacedAt`, `wordingFix: true` for a wording fix, and `restart: true` when the branch was restarted from it). A changed-answer branch records `revisesAnswer`. A question can carry the user's `rating` (`good` or `bad`) with optional `ratingReason`, `ratedAt` and `ratedBy`; `dismissedAt` (and `dismissedBy`) when set aside; and `replacedBy` / `replaces` linking a regenerated question to its replacement (`replacedBy: "pending"` while the replacement is on its way, which keeps the branch waiting). An open question can record `deferredAt` when the user saved it for later; it stays open but no longer blocks its branch. The pure helpers `isOpen`, `isBlocking` and `effectiveAnswerState` in `assets/questions.js` define these rules for the Store, views and browser. A question from a changed premise optionally records `supersededAt`; its actual answer remains unchanged as history, and unanswered earlier questions no longer require an answer. Sources retain an HTTP(S) URL, descriptive title, the supported/challenged proposition, and retrieval timestamp.

- Work states: `suggested`, `queued`, `running`, `awaiting-answer`, `explored`, `interrupted`.
- `explored` is terminal for that branch. New terminal results record optional `completedAt`; older snapshots infer completion from explored state or a successful terminal job. A changed-premise child optionally records `revises` referencing its earlier investigation. These additive fields do not change schema version 1. Public responses expose derived `completed` for UI behavior.
- A node can carry `options`, `optionsLimit` and `recommendation` from its current result (see the bridge reference). They are the agent's comparison, never a decision; a stale result keeps them only in job history, and revising the premise clears them.
- A map can carry the user's goal (A1): `mode` (`understand`, `decide`, `design`, `diagnose` or `challenge`), `objective` and `successCriteria` (text, at most 2,000 characters each), and `guidanceUpdatedAt`. Absent means not set; older maps are never given a mode. A claimed job that was given the goal records that `guidanceUpdatedAt`. Undo and restore bring the goal back with the rest of the map, and stamp `guidanceUpdatedAt` when it changes. The stored names (`set-guidance`, the `guidance-changed` event, `guidanceUpdatedAt`) keep the issue's word on purpose; agents see the goal as `goal`.
- A map can carry `glossary`: entries `{ id, term, definition, status: "agreed"|"proposed", origin: "user"|"agent", replaces?, jobId?, createdAt, updatedAt }`. Absent means empty. Terms are unique among agreed entries, ignoring case; at most 100 agreed. The user adds, edits, removes, accepts and dismisses them; the agent only proposes. Agreed terms go to packets; editing the glossary changes no idea, so nothing goes stale.
- A node can carry `claims` from its current result: up to 12 `{ id, text, support: [{ source, passage, locator? }] }`, each `source` a URL among the node's sources; empty support means support unknown. Like limitations, a stale result keeps them only in job history and revising the premise clears them. The view adds `hasFindings`; findings with no sources are shown as reasoning.
- A node can carry `limitations` from its current result: up to 8 records `{ id, kind, summary, nextStep, sources?, optionIds?, blocksRecommendation? }`, where `kind` is `conflict` or `missing-evidence`. They are the agent's account of what is unresolved, not conclusions. Like options, a stale result keeps them only in job history and revising the premise clears them. A node without them may predate them, so their absence never means none were found.
- A flagged node records why in `reviewCauses` (`{ sourceId, kind, at }`, where `kind` is `premise-revised`, `premise-forked`, `answer-changed`, `branch-restarted` or `result-during-change`; the newest 20, with `earlierCauses: true` when older ones were dropped). Resolving a flag records `reaffirmedAt` or `clearedAt` (and `replacedBy` when re-explored) and `resolvedBy`.
- Review states: `unreviewed`, `accepted`, `cleared` (no longer relied on). Staleness is separate from review; a previously accepted finding can need review after a premise changes.
- Attribution: an answer optionally records `answeredBy: { name }` and an accepted node `acceptedBy: { name }`, using the Git name (`git config user.name`) of the person running the server. The email is never read. Without a Git name nothing extra is recorded and `acceptedBy` keeps its older value `'user'`. Names are labels, not logins, and never appear in work packets or briefs.
- Graph edges: `contains`, `depends_on`, `supports`, `contradicts`, `related_to`. An edge the user recorded has `addedBy: "user"` and an optional `note`; edges without `addedBy` came from results. A visual parent is not an evidence relationship. Dependency links inform context and staleness; they do not automatically activate/schedule other nodes.
- Jobs retain their input-context fingerprint, visible results, worker name, timing and packet character count. A running job stores `claimHash`, the SHA-256 of its claim key, never the key itself: the key is returned once in the work packet and is kept by the CLI in `.explore/claims/`. Maps written by earlier versions keep `claimKey` until their next save, which replaces it with `claimHash`. Neither appears in map API responses, briefs or version files; only `/api/next` returns the key, once. A late result whose relevant context changed is retained for review instead of replacing the current premise.
- An investigation job saved with warnings from the result checks keeps their codes as `resultWarnings: [{ code, field }]` (see the bridge reference); no text from the result is copied.
- An investigation job may keep `execution: { delegated, model, note? }`: how the agent says it ran the work (Z5), beside `worker` and never in `result`. It is the agent's own report; Explore cannot verify it.
- A job's optional `type` names its kind of work; a missing type means `investigate`, the branch investigation, so older maps behave unchanged. Only investigations change an idea's status, findings, questions, completion or growth history. Other types keep their result on the job record. Work covering the whole map has `nodeId: null`; work about one question records it as `subjectId`.
- Restarting a branch (`restart-branch`) is the one change that deletes ideas. The ideas below it, by containment only, are removed with their jobs, `view.positions` and links, after a named checkpoint version holds them. The restarted idea keeps its premise and answers; its earlier jobs record `restartedAt` and no longer count as its findings or completion, and its node view lists them under "Earlier result before this branch was restarted". The event `branch-restarted` names the checkpoint. Growth batches keep the deleted IDs; growth history ignores ideas that no longer exist, and generated node views of deleted ideas are removed.
- Storage (J5): `GET /api/storage` reports file lengths per map (map file, generated Markdown, history versions) and for `.explore/` claims and the usage log. `POST /api/storage/preview { mapIds?, keepNewest: 5 | 10 | 25 }` lists the unnamed, unimported versions beyond the newest kept, never the newest version or those Undo needs; `POST /api/storage/clean { previewId }` removes only those, rechecking each, within 15 minutes. Maps, Markdown, named versions and `.explore/` are never removed.
- `library: { pinned, archived, archivedAt? }` (I1) is pin and archive state, shared through Git. Missing means neither. Changing it records no event and no version, and a pull that changes only it is not an outside change.
- `view.positions` is presentation state. A layout change does not alter content fingerprints.

The server serializes mutations and writes/syncs a temporary snapshot before replacing `map.json`. Interrupted temporary files are not read as committed snapshots. One server writes a workspace; people share maps by committing and pulling them, not by writing the same files at once. This is not a guarantee against every filesystem/power-loss failure. Generated Markdown is not part of the authoritative transaction.

## Changes from outside Explore

Maps are shared through Git, so `map.json` can change underneath a running server, for example after `git pull` or a branch switch. The server remembers a SHA-256 `fingerprint` of the exact bytes it last wrote or adopted for each map. A map's next read adopts what is on disk, even an older revision, and reports `outsideChange: { at, preserved, inGit }`. The first read after the server starts adopts silently. The version that was replaced is kept: if Git does not already have those exact bytes, they are copied to `ideas/<map-id>/preserved/<time>-<fingerprint>.json`, once per version; ordinary pulls of committed work add no files.

An edit made from the replaced version is refused with code `changed-outside` and writes nothing, even when the revision numbers match. The browser sends the `expectedFingerprint` of the version it shows. Every save also checks that the file is still the version the change was based on.

The rules for a readable map live in `scripts/map-validation.mjs`: the server and `validate.mjs` share them, so CI and the server agree. Map files are strict UTF-8; a leading byte-order mark is ignored. A map that cannot be read is listed as `{ id, unreadable: true, problem }`, where `problem` is `invalid-utf8`, `conflict-markers`, `invalid-json`, `unsupported-version` or `invalid-map` (missing parts, or a file copied from another map's folder). It is never rewritten, the other maps still open, and errors never quote its contents. Fix the file, for example by resolving the Git conflict, and it opens again.

## Growth history

Optional schema-1 `growth: { version: 1, batches: [...] }` records graph additions. Each batch has a strictly increasing `sequence`, an ISO `at` timestamp, `nodeIds`, and `edges` containing `{ from, to, type }` identities. One graph-adding transaction produces one batch, including an edge-only result; its new nodes and edges share that timestamp in `createdAt`. Sequence preserves transaction order when timestamps tie or the clock moves backward. Duplicate suggestions, connections and result deliveries do not add duplicate history. The ledger and graph commit in the same canonical snapshot. Work changes, answers, findings, review and layout do not create growth batches, and routine context packets omit the ledger.

The browser's shared `history.js` provides pure `growthTimeline(map)` and `mapAtGrowthStep(map, index)` functions. Steps contain cumulative node IDs/counts and connection counts, the additions at that boundary, `at`, and `kind` (`recorded`, `dated`, or `unknown`). The first step is the earliest available addition group, and `latestStep` is the final index (`-1` for an empty graph). Projection returns a detached copy, filtering only graph membership. It uses **today's findings, statuses and layout**, and does not reconstruct historical content or work states. Browsing is read-only and never queues work or changes the saved view.

Older maps are readable without migration or writes. Their available `createdAt` dates form deterministic date groups before recorded batches; equal dates form one group. Missing or invalid dates remain unknown. An undated connection is never assigned its endpoints' dates. Unknown additions appear in a final explicitly undated step, which does not assert when they happened. Connections with dates inconsistent with their endpoints also appear in that step; no connection appears before both endpoints. `incomplete`, `unknownNodeCount`, and `unknownEdgeCount` expose these limits. This is a view of known additions, not a claim to exact historical snapshots. First recording a new batch leaves legacy timestamps and connections untouched.

## Version history

Each saved content change is also kept as a version, so anyone who pulls can preview, undo and restore. Versions live in `ideas/<map-id>/versions/` and are committed with the map. Each is one standalone file named `<UTC time>-<6 hex>.json`, holding `{ format: "explore-version", version: 1, mapId, revision, at, author?, labels, name?, checkpoint?, contentHash, map }`, where `map` is the full snapshot without claim data (`claimKey`, `claimHash`, `inputSignature`). There is no index file: the list comes from scanning the folder, so two people's versions merge in Git as separate files without conflicts, and the file name is the version's identity.

- Recording: the version is written just after `map.json` is replaced, inside the same lock, so no version ever shows content that was not saved; if the process stops in between, that one change has no version. `labels` are the event types of that change, and `author` is the contributor's Git name when known. Moving ideas, claiming work and restart bookkeeping (`started`, `interrupted`) are not versions. A snapshot identical to the newest version is not written again. If recording fails the map is still saved and the failure is reported.
- Retention: every named version and every imported copy (`kept: true`), plus the 50 newest others, with unnamed versions capped at 16 MiB per map; the newest is always kept, and so is everything Undo walks or restores for anyone who saved a version (`removable` in `scripts/versions.mjs` is the one rule, shared with the storage cleanup). At most 10 names, 1–120 characters, unique per map. A checkpoint (`checkpoint: true`) is a version Explore names itself before a restart, "Before restarting <title>, <date>"; it is kept like any named version and does not count toward the 10. When the newest version already holds the map and has no name, that version is named instead of copied. Once the user renames or unnames it, it is an ordinary version. Pruning removes files from the folder; committed versions remain in Git history.
- Pinned answers (Z11) are `view.pinnedAnswers`: up to three `{ nodeId, questionId }` in pin order, set by the user's `pin-answer` action. They are shared view state: saving them records no version, a change to them alone (for example from a pull) is not reported as an outside change, a restore keeps today's, and they never reach a brief or a work packet. Entries that name no idea are kept until unpinned and shown as unavailable.
- Restore (`restore-version` with `version`, user-only) replaces the title, original idea, ideas, connections and jobs with the version's. It keeps the event log and growth history, which only grow, and today's positions for ideas that still exist. It is refused while work is running and when the map already matches; queued work is cancelled, and the preview says how much (`queuedCancelled`). Work that was active in that version comes back `interrupted`, so an old claim cannot deliver into the restored map, and nothing starts until the user retries. A restore can reopen a finished branch; the preview lists every such branch. The restore is itself a new revision and version, so it can be undone. The browser's Undo is a restore of the version before the user's latest change, sent with `undo: true` and recorded as `change-undone`.
- Restoring one branch (`restore-branch` with `nodeId`, `version` and the preview's `previewHash`, user-only; preview at `GET /api/maps/:id/versions/:version/branch?node=ID`) brings back that idea and everything below it as the version had them, with their jobs, and leaves the rest of the map as it is. Ideas added inside the branch since are removed with their links and positions. Links inside the branch come from the version; links across its edge are kept from today or taken from the version when both ends exist; links outside are untouched. Survivors keep today's positions and ideas brought back get the version's. Restored findings are flagged (`restored-context-changed`) when an ancestor or an outside prerequisite changed since the version, and outside ideas that depend on what changed are flagged (`branch-restored`) with their questions set aside, as after a revised premise. It is refused for the root, a parent that no longer exists, an ID now elsewhere in the map, queued or running work in the branch, no change, or a preview that no longer matches. It is one new revision and version (`branch-restored`), so Undo reverses it, and it starts no research.
- Recovery (J2): a map whose `map.json` cannot be opened still lists and previews its versions, each checked by the live map's rules (unusable ones say why; version files that cannot be read are listed as `unusable`). `POST /api/recover-copy { mapId, version }` copies a usable version out as a new, separate map with a new ID, `recoveredFrom: { mapId, version, revision }` and no queued or running work; the original folder is never changed. The doctor names maps that cannot be opened. A version is usable by the rule that opens a map (`readProblem`), so whatever the list offers can be copied. The preview is a picture of the version, drawn as the SVG export draws it, rather than the full Constellation: a map whose file cannot be opened has no live map to show it in, and a picture can take no action. Copy the version out to read its findings and answers.
- When a pull or branch switch replaces `map.json`, the replaced content is recorded as a version labelled `before-outside-change`, unless version history or Git already has it. Copies kept in `ideas/<map-id>/preserved/` before version history existed are imported as versions labelled `preserved`, with their original time, when the server starts; the folder is removed only once every copy is in version history. A damaged version, or one saved by a newer Explore format, is refused rather than restored.
- Versions can contain earlier wording of answers the user later rewrote. Maps saved before this feature have no earlier versions; the list reports `earlierMissing`.

Machine-local connection tokens, process locks, result drafts, and claim-delivery files live under `.explore/`, which should be ignored by Git. Settings are not machine-local; they live in `ideas/settings.json`. No model API key is part of a map. A provider's original chat history or conversation ID is not necessary to read/continue the map. Share saved maps deliberately: they contain the user's actual ideas and answers.

## Git status

`GET /api/maps/:id/git-status` reports where a map's `map.json` stands in Git: `{ state, staged?, unstaged?, untracked?, branch?, detached?, upstream?, checkedAt }`. The states are `committed`, `not-committed`, `ignored`, `conflict` (Git still lists the file as unmerged), `no-repository` and `unknown` (Git missing, a timeout, refused access or unexpected output). `branch` is the branch name; a detached HEAD has `detached: true` instead. `upstream` is absent when none is set, `{ ahead, behind }` against the local upstream ref, or `{ gone: true }` when its branch no longer exists; Explore never fetches. Every Git command runs through `scripts/git.mjs`, which is read-only: literal arguments, no shell, no optional locks, fsmonitor off, a 5-second timeout and a 64 KiB output cap, English messages, and none of the inherited variables that would point Git at another repository, index or object store. It works for a map that cannot be opened, and it never returns paths or Git's own output. A missing map is `404` with code `not-found`. The label describes `map.json` only; the generated Markdown beside it may differ from Git.

## Export and import

Diagram exports (Mermaid, JSON Canvas, SVG and the printable page, made by `assets/export-formats.js` in the browser and the CLI) are one-way views of the live map or one branch: they are never imported.

A read-only viewer file (`POST /api/maps/:id/viewer` with `{ expectedRevision, nodes: [{ id, answers, findings }] }`, built by `scripts/viewer.mjs` from the saved map) holds only the ideas the user chose: title, kind and states always, answers and findings with sources only when chosen, a parent link only to a chosen parent, and the app's layout. The map's text sits in a JSON block and reaches the page only as text; a Content-Security-Policy allows just the file's own script and style by hash, so it fetches nothing. Jobs, history, workers, claim keys, paths and the server token never go in. A stale revision, more than 500 ideas or more than 4 MiB is refused. The browser shows the file's text as a preview and downloads only that preview, for the same selection at the same revision.

An export is `{ format: "explore-map", version: 1, exportedAt, map }`, where `map` is the saved map without claim data (`claimKey`, `claimHash`, `inputSignature`). Everything else travels, including history, growth, positions and settings that live in the map. Nothing from `.explore/` is read.

An import accepts an export or a bare format-1 `map.json`. It is untrusted data and must pass the validator (`scripts/map-validation.mjs`) with no errors, or nothing is written. Then one of four things happens:
- **No map with that ID:** the map is saved under its ID. A copy (asked for, or when the ID is taken) gets a new ID and "(copy)" in its title; pin and archive state stay with the original.
- **Identical content:** if a map with that ID matches (ignoring `revision`, `updatedAt` and claim data), nothing is written and the existing map opens.
- **Different content:** the import is a conflict. Nothing is written, and the user may import a copy instead.
- **A copy:** asked for, or the ID is outside the `map-` + 8 hex format. It gets a new map ID, a " (copy)" title and `importedFrom: { mapId, revision, exportedAt }`. Idea IDs and content are unchanged.

Queued or running work arrives `interrupted` and releases what it held, so nothing runs until the user retries. The map's history is unchanged: the import names its first version `map-imported`. A folder with the map's ID that cannot be opened (even one without `map.json`) counts as taken, and a new map is only ever saved where no file exists yet. Imports are limited to 5,000 ideas.

## Reading procedure

Read the map overview, then the selected node and related evidence. Check status and staleness before treating a finding as accepted knowledge. Prefer the CLI's bounded section reads with question IDs or a query, continuing only necessary pages at the same revision. Linked node Markdown remains a fallback; avoid loading a long history to answer one targeted question. Never load the whole snapshot merely to resume an investigation.
